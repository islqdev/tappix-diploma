Описанные функции не устанавливают безопасность, качество локализации или
готовность к требованиям конкретного заведения. Цены и договорные условия не
сравниваются без одинакового объёма услуг. Утверждение «Tappix лучше конкурентов»
из этой таблицы не следует: аналоги уже покрывают значительную часть сценария.

## Ручные альтернативы

Бумажная карта проста для запуска, но в выбранной модели не даёт общей истории
владельцу. Таблица позволяет учитывать события без отдельной подписки, но требует
дисциплины ручного ввода и управления доступом. Это аналитические предположения,
которые нужно проверить наблюдением. «Ничего не менять» рационально, если затраты
и неудобство новой системы выше ожидаемой пользы.

Проверяемое предложение Tappix: отдельная веб-карта и сканер без обязательной
замены кассы, ограниченный набор понятных метрик и управление несколькими
независимыми компаниями. QR/NFC только открывает или идентифицирует карту;
само сканирование гостем не даёт права начислить визит. Различимость предложения,
готовность платить и необходимость отдельного сервиса пока не подтверждены.

## Выбор технологий

Решения ниже предварительные: стек задан командой, а не выбран по выдуманному
бенчмарку. Каждая группа содержит выбранное решение и две альтернативы.

| Решение | Сильная сторона в контексте | Цена выбора и ограничение |
| --- | --- | --- |
| Go API — выбран | Отдельная серверная граница, стандартные HTTP/тестовые средства T5 | Два языка в команде; OpenAPI и валидацию надо поддерживать |
| Node.js/TypeScript | Общий язык с frontend, событийная модель T6 | Общий язык сам по себе не обеспечивает изоляцию и транзакции |
| Python/FastAPI | Типизированные входные модели, генерация OpenAPI T7 | Потребуется смена согласованной backend-зоны и освоение экосистемы |
| PostgreSQL — выбран | Транзакции, связи между tenant-сущностями, возможность RLS T1/T2 | Нужны миграции, индексы и проверка политик; RLS не включается сам |
| MySQL/InnoDB | Реляционная транзакционная модель T3 | Нужно заново согласовать схему и стратегию tenant-защиты |
| MongoDB | Гибкие документы и многодокументные транзакции T4 | Связанный учёт карт, визитов и леджера требует явных правил согласованности |
| Next.js/React — выбран | Роутинг и серверный/клиентский UI в React framework T8/T9 | Нельзя дублировать бизнес-правила Go в UI или считать UI проверкой доступа |
| React SPA | Можно отдельно выбирать сборку, роутинг и работу с API T9 | Больше самостоятельных решений по структуре и состояниям приложения |
| Vue | Компонентный подход и поддержка разных вариантов приложения T10 | Потребуется пересмотр согласованной frontend-зоны и шаблонов компонентов |

Выбор Go + PostgreSQL + Next.js согласуется с разделением ответственности студентов
и транзакционным ядром. Быстродействие и экономичность этого сочетания ещё не
измерены. Redis T11 предлагается для сессий, rate limit и временных данных;
события лояльности и постоянный отзыв доступа сохраняются в PostgreSQL.
При недоступности проверки доступа операции записи должны отказывать безопасно.

## Что требуется проверить

На следующем этапе сравнить реальное время выдачи карты и отметки визита с
бумажной карточкой; отдельно проверить удобство при очереди и плохой сети.
Для аналогов остаются непроверенными точные роли, тарифные ограничения,
казахская локализация, экспорт полной истории и условия хранения данных.
